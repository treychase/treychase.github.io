The daily report

What loads on the front page

The landing view covers the full slate from the previous day. Every game is summarized from the MLB Stats API, alongside the individual performances worth knowing about and month-to-date leaderboards that put the day in context.

  • Box and line scores

    Every game from the previous day, parsed from the MLB Stats API, with the line score alongside the full box.

  • Top performances

    The day's standout hitting and pitching lines, surfaced rather than buried inside a game.

  • Monthly leaderboards

    Month-to-date hitting leaders from Baseball Savant and pitching leaders from Baseball Reference, so a single game reads against a recent baseline.

  • Standings

    Tidy per-team standings by division and league, and the entry point into a team's win-projection history.

Player cards

Click any name, anywhere in the app

Names are click-through everywhere they appear — box scores, leaderboards, the pitch run value table. The card that opens is precomputed rather than fetched live, so it appears immediately.

  • Season card

    Bio, season line, Statcast percentile rankings, splits, and Wins Above Replacement.

  • Pitch arsenal and Stuff+

    Pitch mix and usage with FanGraphs Stuff+ per pitch, for a read on what a pitcher actually throws.

  • Movement profile

    Induced break and pitch movement per pitcher, plus arm angle and extension expressed as a league percentile and z-score.

  • Batted ball and spray

    Batted-ball and bat-tracking data behind a spray chart, with ground ball, fly ball, and line drive rates.

  • Sprint speed

    Placement against the league sprint-speed leaderboard.

On which WAR Leaderboards and cards report FanGraphs fWAR. Baseball Reference bWAR is used only when FanGraphs is unavailable, and a lightweight estimate is the last resort — the label on each card says which source it used, so the number is never silently swapped.

Pitch Run Value

Ranking pitches, not pitchers

Built from Baseball Savant's pitch-arsenal leaderboard, this tab carries one row per pitcher per pitch type, so a reliever's slider is rated on its own rather than folded into a season line. Dropdowns filter by team and pitch type, and a minimum-pitches box sets the sample-size floor; the underlying dataset is fetched at a loose minimum, so tightening the filter never triggers a refetch.

Alongside total run value and RV/100 the table carries usage, the results the pitch allowed — batting average, slugging, and wOBA — and its whiff, strikeout, and hard-hit rates. Every column sorts, and clicking a row opens that pitcher's card.

Sign convention Run value is signed from the pitcher's side, matching the raw Savant field and the RV/100 percentile on the pitcher card: a positive figure means the pitch saved runs. Rows sort descending, so the league's best pitches sit at the top.

Win Projections

A recursive Bayesian filter, carried day to day

Each team's latent per-game win probability is held as a Beta belief that is updated once a day and carried forward, rather than refit from scratch.

Prior Beta(34, 34) — mean .500, sd(θ) ≈ .060
Update carry yesterday's (α, β) → apply forgetting factor → fold in the day's W/L
Projection final wins = wins banked + BetaBinomial(games remaining; α, β)
Interval 90% credible, from the BetaBinomial quantiles

The prior's strength is tuned to the league's actual talent spread, so a 5-0 start is regressed toward average rather than extrapolated toward 162-0. The forgetting factor lets recent form count for a little more than April without discarding it.

Because the model runs inside the daily refresh and persists its state, the tab reads a precomputed result and fits nothing on page load. It shows a per-team chart of how a projection and its interval have moved across the season, and a status badge that turns amber when the underlying dataset is stale and red when it is missing — so a number on screen is never quietly out of date.

Betting props

Posterior-predictive pricing with matchup covariates

A player's game log becomes a distribution for the next game, off which over/under probabilities and vig-free fair odds are read.

Counts hits, home runs, total bases, strikeouts
          Gamma–Poisson → Negative-Binomial predictive
Innings Normal–Inverse-Gamma (unknown mean and variance) → Student-t predictive
Priors league-average, so a 3-for-6 start regresses rather than extrapolates
Matchup multiplicative shift (≈ 1 is neutral) from opposing pitcher and lineup, park factor, and platoon split

The matchup covariates are selectable, so a line can be read neutral or against a specific opponent and park.

How the data gets there

Precomputed each morning, never fetched on page load

Hitting the MLB, FanGraphs, and Savant endpoints on every page load would be slow and fragile. Instead the slow datasets are rebuilt once a day, validated, and published; the app reads those files and only falls back to a live request when one is missing.

1

Scheduled job · daily 08:00 ET

A GitHub Actions workflow runs the refresh script on a schedule.

2

Fetch and precompute

Schedule, box and line scores, standings, season leaderboards with fWAR, month-to-date leaders, and Stuff+ — plus a per-player dataset for every person appearing in the day's box scores and leaderboards, so a player card is instant.

3

Validate before publishing

Schema and content checks run over every dataset, so a malformed fetch never overwrites a good one.

4

Publish to a dataset repo

The validated files are uploaded to a Hugging Face dataset repository.

5

App reads, with a live fallback

The dashboard prefers a local copy, then the published one, validating again after loading. Anything corrupt or stale is ignored and the fetcher transparently falls back to a live request.

The win-projection state is part of this: one row per team per day carrying the Beta parameters and the projected wins, appended on each refresh. That is what makes the filter genuinely recursive rather than a nightly recomputation.

Engineering

What keeps it running unattended

  • Split fetchers

    Every fetcher is split into a live network call and a load-or-live wrapper, so the same code path serves both the refresh job and the app.

  • Validation on both sides

    Datasets are validated before publishing and again after loading, so bad data fails closed instead of reaching the screen.

  • Continuous integration

    The test suite sources every module, which doubles as a load check, and covers helpers, data processing, validation, the offline load-or-live wrappers, batted-ball logic, and smoke tests for the UI and plot builders.

  • Automated deployment

    Pushes to main that touch the app or its modules redeploy to shinyapps.io automatically. Only the app code is bundled — datasets are read at runtime.

  • Containerized

    A Dockerfile runs the whole dashboard locally on a single port for development or self-hosting.

The dashboard updates every morning and is open to anyone.
